### What needs to be tested (reasoning only)

This problem has two hard parts:
1) correctly computing the **final array** after many *global* value transformations mixed with appends, and  
2) correctly computing the **inversion count** (discord score) of the final array at scale.

A good test suite should stress correctness of the transformations (especially timing and simultaneity) and correctness/robustness of inversion counting.

## 2) Structural edge cases (array patterns & duplicates)

Focus on final array structures that can expose inversion-count mistakes (especially with duplicates) and mapping mistakes.

- **Already sorted increasing**
  - Appends forming `1,2,3,...` and few/no transforms → inversion count `0`.
- **Strictly decreasing**
  - Appends forming `n,n-1,...` → inversion count maximum `n(n-1)/2` (forces 64-bit).
- **All equal**
  - Many appends of the same value and/or transforms that collapse values to one number → inversion count `0`.
- **Many duplicates with scattered order**
  - Patterns like alternating values (`2,1,2,1,2,1,...`) to test inversion counting when ties exist (equal values should not count as inversions).
- **Transforms that create duplicates**
  - Start with distinct values, then apply `2 x y` mapping many values into one, to ensure inversion counting handles massive duplication correctly.

## 3) Stress conditions / worst-case patterns

These are aimed at breaking slow solutions (e.g., naive “apply transform to whole array each time”).

- **Worst-case for naive transformation**
  - Large `n` (near `5e5`) and large number of transforms (near `5e5`), with transforms frequently referencing values that appear many times.
- **Worst-case for mapping/composition logic**
  - Long chains of remaps: `2 a b`, then `2 b c`, then `2 c d`, etc.  
    These expose incorrect composition handling (note: earlier `a` values are affected by later remaps only insofar as they were changed to intermediate values at the time).
- **Frequent swap/transmute mixing**
  - Sequences where `3 x y` and `2 x y` alternate, forcing correct handling of swap vs one-way replacement.
- **Operations mostly transforms, few appends**
  - Ensures solutions respect that transforms apply only to the current scroll at that moment, and do not incorrectly apply an end-state mapping to elements that were appended after certain transforms.
- **Skewed distribution**
  - Many operations hitting the same small set of values (e.g., only values in `{1,2,3}`) to stress collision-heavy mapping and duplicate-heavy inversions.
- **Random-like heavy tests**
  - Useful to catch logic bugs not covered by structured patterns, particularly in swap handling.

## 4) Common implementation mistakes to target

### Transformation correctness
- **Time-order bug (most important)**
  - A `2/3` operation affects only elements currently present; elements appended later are unaffected by earlier transforms.
  - Tests where many transforms happen, then append, then more transforms—so only the latter set should affect the newly appended element.
- **Mirror-Swap simultaneity**
  - `3 x y` must swap values simultaneously:
    - An incorrect sequential replace (“replace x with y then replace y with x”) will break cases where both x and y exist.
  - Must include tests where both x and y are present in the array at swap time.
- **No-op edge cases**
  - `2 x x` should do nothing.
  - `3 x x` should do nothing.
- **Transforming values not present**
  - `2 x y` and `3 x y` where neither x nor y currently exists are effectively no-ops; still must be handled safely and efficiently.
- **Repeated toggling**
  - Multiple swaps of the same pair (`3 x y` repeated many times) to catch parity errors.

### Inversion count correctness
- **64-bit overflow**
  - Maximum inversions for `n=5e5` is ~`1.25e11`, which overflows 32-bit. Tests must include near-max inversion patterns.
- **Duplicates handling**
  - Inversions are strict (`>`), so equal values must not contribute. Include heavy-duplicate arrays to catch “>=” mistakes.
- **BIT / Fenwick indexing errors**
  - Values include boundary `1` and `5e5`; off-by-one in Fenwick usage can break these.
  - If coordinate compression is used, tests with few distinct values and tests with many distinct values help.

### Output formatting
- `n=1` and large `n` output lines: ensure exactly one line for array and one line for inversion count, with correct spacing/newline handling.
